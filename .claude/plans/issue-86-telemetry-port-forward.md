# Issue #86 — Telemetry pull: scheduled SSH port-forward to aw-server :5600

Roadmap: `docs/roadmap.md` → Phase 5. Architecture: `docs/architecture.md` →
"Inbound (client → server) — telemetry pull".

## Goal (scope boundary)

Deliver the **transport window** only, exactly as the issue frames it
("this one only establishes the transport window"):

1. A pooled **local SSH port-forward** on the merged `transport/ssh` facade
   (#82): a loopback `net` listener → `ssh2 forwardOut` → the client's
   `aw-server` at `127.0.0.1:5600`, with a robust open/run/close lifecycle
   that never leaks a listener, socket, or channel.
2. A **croner-scheduled telemetry-pull job** that iterates enrolled clients,
   opens a forward per reachable client with **bounded concurrency**, skips
   offline clients non-punitively (`SshUnreachableError` → telemetry gap,
   not failure), and confirms the tunnelled `aw-server` is reachable via the
   merged AW REST client (#87). A `consume(baseUrl, client)` seam is left for
   the Phase-5 normalisation (#88) to plug into without reshaping the job.

The AW REST client already documents this exact contract: "opens an SSH
port-forward to the client's aw-server (localhost:5600, never
network-exposed — #86) ... This module only needs the resulting base URL; it
never opens the tunnel itself."

## License boundary

ActivityWatch is reached only over its REST API (#87), through a
server-initiated SSH tunnel **bound to loopback** (AW's API is unauthenticated
and must never be network-exposed). The tunnel is pure TCP forwarding via
`ssh2` — no GPL linkage, no GPL binary in the image. No new dependency
(`ssh2`, `croner`, `zod` already present).

## Phases

### Phase A — facade port-forward
- `SshTransport.withPortForward<T>(target, remote, fn, options?)` in
  `transport/ssh/facade.ts`:
  - reuse the pooled connection (`#resolve` + `#connect`);
  - `net.createServer()` bound to `127.0.0.1:0` (ephemeral, loopback only);
  - per incoming socket → `client.forwardOut("127.0.0.1", localPort,
    remote.host ?? "127.0.0.1", remote.port, cb)`, pipe both ways, destroy the
    socket on a forward error (one bad socket must not sink the window);
  - run `fn({ host, port })`; in `finally` close the server and destroy any
    lingering sockets so nothing leaks; propagate `fn`'s result/throw;
  - connect failure → `SshUnreachableError` (from `#connect`), unchanged.
- Export `PortForwardOptions` / `PortForwardTarget` from `ssh/index.ts`.
- Tests: extend `tests/transport/ssh/facade.test.ts` (add `forwardOut` to the
  ssh2 mock; a `PassThrough` channel echoes through the pipe loop so a real
  loopback socket round-trips bytes; assert teardown / no-leak; unreachable).

### Phase B — telemetry pull job + schedule + config
- `transport/activitywatch/telemetry.ts`:
  - `runTelemetryPull(deps)` → bounded-concurrency map over clients, per-client
    forward + `consume`, offline-skip, error isolation, returns a
    `{ attempted, succeeded, skippedOffline, failed }` summary.
  - default `consume`: build an `ActivityWatchClient` on the tunnel base URL
    and call `getInfo()` to confirm liveness (logs server version).
  - `scheduleTelemetryPull(run, options)` → `new Cron(pattern, { protect:true,
    catch })` wrapper, returns the `Cron` handle for shutdown `.stop()`.
  - `isValidCronPattern(pattern)` helper (mirrors `isValidTimeZone`).
- `config.ts`: `telemetry: { pullCron (default "*/5 * * * *", refined via
  isValidCronPattern), pullConcurrency (default 4) }`; wire `PCT_TELEMETRY_*`.
- Export new symbols from `transport/activitywatch/index.ts`.
- Tests: `tests/transport/activitywatch/telemetry.test.ts` (success summary,
  offline skip, error isolation, concurrency bound, custom consume seam,
  schedule pattern/protect/handle, cron validator) + extend
  `tests/config.test.ts` (defaults, override, invalid cron, invalid concurrency).
