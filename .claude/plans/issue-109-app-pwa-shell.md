# Plan — #109 `/app` SvelteKit route group + PWA basics

Roadmap: `docs/roadmap.md` → Phase 9 (bullets 1–2 + last). This is the
**foundational `/app` surface** that #110 / #111 / #65 / #112 build on.

## Constraints / boundaries

- **No license surface.** Pure frontend (SvelteKit `adapter-static`) + a static
  web-app manifest + a service worker. `/app` talks only to `/api/*` — same
  contract as `/admin` and integrators. No GPL code, no Docker-image change.
- **Stay within #109.** The per-child status screen (#110), parent home /
  quick-grant screens (#111), Web Push (#65) and the per-user PIN auth model
  (#112) are out of scope — this PR ships the *shell* they render into.
- **Don't introduce deep prerendered routes.** `server/src/web/frontend.ts`
  serves only the `/admin` and `/app` *entry* pages; pages use **relative**
  asset paths so they must be served at the slash-free surface URL. Deep
  client-side routes on hard refresh are #59's job. So `/app` stays a single
  prerendered entry; the bottom tab bar is shell chrome with inert placeholders
  until #110/#111 wire real destinations.

## Pieces

1. **App-shell layout** — `src/routes/app/+layout.svelte`: mobile-first shell
   (header with brand + live online/offline indicator, content slot, bottom tab
   bar chrome), drawing on the design tokens in `design/assets/styles.css`
   (`--primary #4f46e5`, `--bg #f4f5fb`). Injects the manifest link + theme
   colour + apple-touch-icon via `<svelte:head>` so **only `/app`** gets them
   (`/admin` keeps the shared root layout untouched). Registers the service
   worker (prod only) from here so a visitor to `/admin` who never opens `/app`
   never gets a worker.
2. **Landing** — `src/routes/app/+page.svelte`: a minimal "My Time" placeholder
   inside the shell, honest that the live status lands in #110.
3. **Web app manifest** — `static/app.webmanifest`: `id`/`start_url`/`scope`
   = `/app`, `display: standalone`, theme/background colours, PNG icons
   (192, 512, maskable-512) + an apple-touch-icon for iOS installability.
4. **Service worker** — `src/service-worker.ts`: precache the hashed `build`
   chunks + chosen `files` + the `/app` prerendered shell; cache-first for those
   immutable assets; network-first-with-`/app`-shell-fallback for `/app`
   navigations (offline-friendly app shell); **never** touch `/api/*`; pass
   everything else (incl. `/admin`) through to the network. Scope `/` (required
   so root-level `/_app/…` chunks are cacheable) but only registered from
   `/app`. Auto-registration disabled in `svelte.config.js` in favour of the
   scoped manual registration above.
5. **Icons** — generated by a committed, dependency-free Node script
   (`scripts/generate-app-icons.mjs`, zlib-only PNG encoder) so the brand-mark
   PNGs are reproducible and reviewable rather than opaque blobs.

## Verification

- `cd server/frontend && npm ci && npm run build` — `svelte-kit sync` +
  `svelte-check` (typechecks the SW) + `vite build` with `adapter-static`
  `strict: true` (fails on any non-prerenderable route). This is exactly how CI
  builds the frontend.
- Manifest is valid JSON with required installability fields; SW logic reviewed
  for the cache-first / network-first / `/api` bypass branches.
- No `server/src` change → the backend vitest coverage gate is unaffected; the
  existing `server/tests/web/frontend.test.ts` static-mount tests still cover
  the wildcard that serves the new `manifest`/`service-worker.js`/icons.
